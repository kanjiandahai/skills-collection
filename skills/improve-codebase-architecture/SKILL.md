# improve-codebase-architecture

先 **看清结构与痛点**，再提可分步落地的架构改进，避免大爆炸重写。

## 何时用

- 改一处坏一片、循环依赖、上帝模块
- 准备拆包、建边界、引入分层/六边形等
- 用户要「架构评审 / 改进结构」

## 工作流

1. **摸底**：目录、关键入口、依赖方向、测试布局；画出当前与目标的简单关系（可用 Mermaid）。
2. **列痛点**：按频率与风险排序（构建慢、难测、改动面、认知负担）。
3. **定原则**：本库提倡的边界（如 domain 不依赖 UI）；写进简短 ADR 或 README 小节。
4. **给迁移切片**：每步可合并、可回滚；先加缝合线（接口/门面）再搬实现。
5. **验证**：关键路径测试、打包/类型检查；大改分 PR。

## 原则

- 依赖指向更稳定的内层；避免基础设施细节泄漏进领域
- 用删除与收缩庆祝进步，而不是只加抽象层
- 文档与代码同 PR 更新，防止「目标架构」只活在幻灯片里

## 成功标准

- 有现状图、目标图、分步计划
- 至少一条高价值切片可独立落地并验证
